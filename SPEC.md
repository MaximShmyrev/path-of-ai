## 1. Контекст проекта

**«Путь ИИ»** — веб-RPG для геймификации изучения ИИ. Прогресс и программа обучения
подаются как олдскульная RPG (Diablo / Dungeon Siege / Dragon Age): герой, карта мира
с регионами-областями ИИ, локации-темы, квесты с обязательной практикой, опыт, уровни,
разблокировка контента. Интерфейс на русском (кроме спец-терминов тем обучения).

**Стек (зафиксирован):**

| Слой | Технология |
|------|-----------|
| Фронтенд | React 18 + TypeScript + Vite |
| Бэкенд | Python 3.12 + FastAPI + Pydantic v2 + SQLAlchemy 2.0 (sync, psycopg v3) |
| БД | PostgreSQL 16 |
| LLM | GLM Coding Plan (Anthropic-совместимый эндпоинт) через шов `StoryGenerator`; детерминированный фоллбэк из seed |
| Тесты (бэк) | pytest + pytest-asyncio, покрытие — coverage, мутации — mutmut |
| Тесты (фронт) | Vitest + Testing Library, мутации — Stryker |
| Статика | ruff + mypy --strict (Python); eslint + tsc --strict + prettier (TS) |
| Запуск | docker compose (frontend, backend, db) |

**Цель:** мотивировать учиться ИИ ежедневно за счёт геймификации; упор на практику —
у каждой темы минимум один практический квест.

**Границы MVP (НЕ входит):** мультиплеер/PvP/соцфункции, платежи, нативные мобильные
приложения, sandbox-исполнение кода ученика.

## 2. Зафиксированные решения (из уточнений)

1. **Стек:** React+TS (фронт) + Python/FastAPI (бэк) + PostgreSQL. Бэкенд — основной
   носитель бизнес-логики, проработанный `python-guidelines.md`.
2. **Пользователи:** один локальный игрок, **без аутентификации**. Один профиль героя
   на инсталляцию, прогресс хранится в БД. (Слой users/auth спроектирован как будущий
   шов, но в MVP не реализуется — см. §11.)
3. **Контент:** **гибрид**. Каркас программы (регионы → темы → квесты, пререквизиты,
   пороги XP) — версионируемый **seed** (YAML), валидируемый схемой. Динамика
   (сюжетные события) — генерируется LLM по ходу.
4. **LLM (события):** **комбо** — основной рантайм-путь через провайдера **GLM Coding
   Plan** (Anthropic-совместимый эндпоинт), с детерминированным фоллбэком из seed-банка.
   Доступ только через шов `StoryGenerator` (adapters). Замечание: «использовать сам
   Claude Code в рантайме» технически невозможно — работающее приложение не может вызвать
   агента из терминала; «Claude/GLM» доступны приложению только как внешний API за швом.

### 2.1 Разрешение противоречия «LLM» ⨯ «docker compose up без ручных шагов»

Критерий требует подъёма «без ручных шагов». Комбо-решение снимает противоречие
полностью (обязательно к соблюдению):

- `docker compose up` поднимает **все** сервисы и БД **без ключа**: при отсутствии
  `GLM_API_KEY` `StoryGenerator` работает через `SeedBankAdapter` (детерминированный
  банк событий из seed). Приложение полностью функционально из коробки.
- **Живая генерация (опционально):** если в `.env` задан `GLM_API_KEY` (и `GLM_BASE_URL`),
  основным становится `GlmAdapter` — генерация событий на лету. Это конфиг-шаг, не
  ручной шаг внутри работы приложения.
- **Деградация:** при сбое/таймауте GLM `StoryGenerator` **молча переключается** на
  `SeedBankAdapter` (событие всё равно возвращается, `200`), факт фоллбэка логируется.
  Прохождение квестов никогда не блокируется генерацией.
- **Детерминированность тестов:** бизнес-логика и её тесты НЕ ходят в сеть — используют
  `SeedBankAdapter`. Живые тесты `GlmAdapter` помечаются `@pytest.mark.live_llm`,
  **исключены из порога покрытия** и из CI по умолчанию; запускаются явно при наличии ключа.

## 3. Глоссарий

**Домен (игровой мир):**

- **Герой** — профиль обучающегося: уровень, XP, характеристики, инвентарь.
- **Карта мира** — визуализация программы: **Регионы** (крупные области ИИ).
- **Регион** — группа тем (ML / LLM / RAG / Агенты …); имеет порог разблокировки.
- **Локация (тема)** — единица обучения внутри региона; имеет пререквизиты.
- **Квест** — учебное задание в теме; ≥1 квест на тему — **практический**.
- **Босс / испытание** — итоговый квест темы.
- **XP / уровень** — опыт и уровни героя; уровень открывает регионы.
- **Лут / артефакт** — награда за квест (значок, разблокировка).
- **Событие** — динамический сюжетный фрагмент, сгенерированный LLM.

**Архитектура (из skill `improve-codebase-architecture`, термины применяются буквально):**

- **module** — что-либо с интерфейсом и реализацией.
- **interface** — всё, что вызывающий обязан знать: типы, инварианты, режимы ошибок,
  порядок, конфиг.
- **implementation** — код внутри.
- **depth** — много поведения за маленьким интерфейсом (deep = высокий рычаг).
- **seam** — место, где живёт интерфейс и где поведение можно подменить без правки на месте.
- **adapter** — конкретная реализация интерфейса на шве.

## 4. Архитектура

### 4.1 Принципы

- **Зависимости направлены внутрь.** Ядро (`progression`, `catalog`, `quests`) не знает
  про FastAPI, SQLAlchemy, HTTP и Claude. Фреймворк/БД/LLM — **adapters** на внешних швах.
- **Глубокие модули.** `progression` — самый глубокий: маленький интерфейс
  (`award_xp`, `level_for_xp`, `recompute_unlocks`), много правил внутри.
- **Тест через интерфейс.** Поведение проверяется через публичный интерфейс модулей и
  через HTTP API, а не через детали реализации.
- **Два adapter'а = настоящий шов.** Каждый шов имеет ≥2 адаптера (боевой + тестовый),
  что доказывает его реальность (deletion test).

### 4.2 Карта модулей (бэкенд)

### 4.3 Модули и интерфейсы (что обязан знать вызывающий)

#### `progression` — ядро прогресса (deep, чистые функции, без I/O)

- **interface:**
  - `level_for_xp(total_xp: int) -> int` — уровень по суммарному XP.
  - `xp_to_next_level(total_xp: int) -> int` — сколько XP до следующего уровня.
  - `class_modifier(hero_class: HeroClass, region_id: RegionId) -> float` — множитель XP
    класса героя для региона (напр. «Маг моделей» ×1.1 в регионе LLM, иначе ×1.0). Чистая.
  - `award_xp(state: HeroState, base_amount: int, modifier: float) -> XpResult` —
    начисляет `round(base_amount * modifier)` XP, возвращает новый стейт + факт level-up
    (без мутации входа).
  - `recompute_unlocks(hero: HeroState, catalog: Catalog) -> UnlockState` — какие
    регионы/локации открыты при текущем уровне и завершённых темах.
- **кривая уровней:** порог уровня `N` = `base_xp * N²` (квадратичная), `base_xp` — из
  seed-конфига. `level_for_xp` детерминирован от `total_xp`.
- **инварианты:** XP монотонно неубывающий; `base_amount > 0`, `modifier > 0`; уровень
  детерминирован от XP; функции **чистые** (без побочных эффектов, не мутируют аргументы).
- **режимы ошибок:** `ValueError` при `base_amount <= 0`, `modifier <= 0` или отрицательном XP.

#### `catalog` — каталог контента (deep)

- **interface:** `load() -> Catalog`; `Catalog.region(id)`, `Catalog.topic(id)`,
  `Catalog.quest(id)`, `Catalog.prerequisites(topic_id) -> list[TopicId]`.
- **инварианты (валидируются при загрузке, fail fast):** уникальные id; ссылки на
  пререквизиты существуют; **граф пререквизитов ацикличен (DAG)**; у каждой темы ≥1
  практический квест; пороги XP регионов неубывающие.
- **seam:** `ContentSource` (`YamlContentSource` — боевой; `InMemorySource` — тесты).

#### `quests` — прохождение квеста (оркестрация)

- **interface:** `complete_quest(quest_id, submission) -> CompletionResult` — проверяет
  доступность темы (через `progression.recompute_unlocks`), валидирует сдачу, начисляет
  XP (через `progression.award_xp`), сохраняет (через `StateStore`), возвращает
  результат (новый уровень, разблокировки, лут).
- **инварианты:** XP/уровень меняются **только** здесь, через `progression`; идемпотентность
  повторной сдачи уже завершённого квеста (не начисляет XP дважды).
- **режимы ошибок:** `LocationLocked`, `QuestNotFound`, `InvalidSubmission`.

#### Швы (seams) с адаптерами

- **`StateStore`** — персистентность героя/прогресса. Adapters: `SqlAlchemyStore`
  (Postgres), `InMemoryStore` (тесты). interface: `load_hero()`, `save_hero(state)`,
  `quest_status(quest_id)`.
- **`ContentSource`** — источник seed-контента. Adapters: `YamlContentSource`,
  `InMemorySource`.
- **`StoryGenerator`** — генерация событий. interface:
  `generate_event(ctx: EventContext) -> StoryEvent` (асинхронный). Adapters:
  `GlmAdapter` (GLM Coding Plan, Anthropic-совместимый SDK: тот же код, иной `base_url`
  + ключ), `SeedBankAdapter` (детерминированный банк из seed — фоллбэк и тесты).
  Контракт: всегда возвращает русский текст в каноне RPG; **не бросает** наружу при сбое
  провайдера — внутренне переключается на `SeedBankAdapter` и логирует фоллбэк.
- **`api`** — adapter на HTTP-шве (FastAPI). Тонкий: схемы запросов/ответов (Pydantic),
  маппинг доменных ошибок → HTTP-коды. Не содержит бизнес-правил.

### 4.4 Фронтенд (модули)

- **`ApiClient`** (seam над HTTP; `HttpApiClient` + `FakeApiClient` для тестов UI).
- **`gameStore`** — состояние игры (герой, карта, текущая локация).
- **Сцены (RPG UI):** `CharacterCreation`, `WorldMap`, `LocationView`, `QuestView`,
  `LevelUpOverlay`, `EventDialog`. Все строки — русские, через единый словарь `ru.ts`.
- **`theme/assets`** — слой графики (ассеты от Claude Designer, см. §10).

### 4.5 Направление зависимостей (правило, проверяемое в ревью)

`api → quests → {progression, catalog}`; `quests → StateStore/StoryGenerator (интерфейсы)`.
**`progression` не импортирует ничего из `api`, `db`, `llm`.** Нарушение — стоп-фактор ревью.

## 5. Модель данных

### 5.1 Схема контента (seed, валидируется Pydantic-схемой)

```yaml
progression:
  base_xp: 100                 # порог уровня N = base_xp * N²

classes:                       # стартовые классы героя (модификаторы XP)
  - id: model-mage
    title: "Маг моделей"
    avatar_ref: "classes/model-mage.png"
    modifiers: { llm: 1.10 }   # ×1.1 XP в регионе llm, иначе ×1.0

regions:
  - id: ml-foundations
    title: "Основы машинного обучения"
    unlock_level: 1            # порог уровня героя
    topics:
      - id: supervised-basics
        title: "Обучение с учителем"
        prerequisites: []      # id других тем
        quests:
          - id: sb-theory
            title: "Свиток теории"
            kind: theory        # theory | practice | boss
            xp: 50
          - id: sb-practice
            title: "Испытание: обучи классификатор"
            kind: practice      # ≥1 practice на тему — инвариант
            xp: 150
            quiz:               # автопроверяемая сдача (sandbox нет)
              - q: "Что делает обучение с учителем?"
                options: ["...", "...", "..."]
                answer: 1       # индекс эталонного ответа (хранится только на сервере)
```

**Объём MVP-программы:** 3–4 региона (ML → LLM → RAG → Агенты), ~12 тем.
Сдача практического квеста = **квиз с автопроверкой**: эталонные `answer` хранятся
только на сервере и не отдаются клиенту (анти-чит).

### 5.2 Сущности БД (PostgreSQL)

- `hero` — `id`, `name`, `class`, `avatar_ref`, `total_xp`, `created_at`. (Один ряд в MVP.)
- `quest_progress` — `hero_id`, `quest_id`, `status (locked|available|completed)`,
  `completed_at`, `awarded_xp`. Уникальность `(hero_id, quest_id)`.
- `story_event` — `id`, `hero_id`, `location_id`, `text`, `created_at` (кэш сгенерированных
  событий, для воспроизводимости и истории).

Контент (регионы/темы) **не** хранится в БД — он в seed (источник истины — файлы).

## 6. API (контракт)

| Метод | Путь | Назначение | Ошибки |
|-------|------|-----------|--------|
| POST | `/api/hero` | Создать героя (имя, класс, аватар) | 409 если герой уже есть |
| GET | `/api/hero` | Текущий герой + уровень + XP | 404 если нет |
| GET | `/api/map` | Карта мира: регионы/локации со статусами | — |
| GET | `/api/topics/{id}` | Тема + её квесты + доступность | 404, 423 (locked) |
| POST | `/api/quests/{id}/complete` | Сдать квест (submission) | 404, 423, 422 |
| POST | `/api/locations/{id}/event` | Сгенерировать событие (GLM или фоллбэк-банк) | 200 всегда (с пометкой `source: glm\|bank`) |

- Статусы: `423 Locked` для заблокированной локации; `422` — невалидная сдача;
  `409` — повторное создание героя.
- `/event` всегда `200`: при сбое GLM возвращается событие из банка с `source: "bank"`.
- XP/уровень **никогда** не принимаются от клиента (анти-чит, см. §7 и §8).

## 7. BDD-сценарии тестов

Каждый пользовательский сценарий из задачи → минимум один тест-сценарий. Формат
Given/When/Then. Уровень: `[unit]` ядро, `[api]` через HTTP, `[ui]` фронтенд, `[e2e]`.

### 7.1 Создание героя

```gherkin
Сценарий: Создание героя при пустом профиле        [api]
  Дано героя в системе нет
  Когда POST /api/hero с валидными именем/классом/аватаром
  Тогда создаётся герой уровня 1 с total_xp = 0
  И GET /api/map возвращает один открытый стартовый регион (unlock_level = 1)

Сценарий (негативный): Повторное создание героя     [api]
  Дано герой уже существует
  Когда POST /api/hero повторно
  Тогда ответ 409 и существующий герой не изменён

Сценарий (граничный): Пустое/слишком длинное имя    [api]
  Дано POST /api/hero с пустым именем (или > 40 символов)
  Тогда ответ 422 и герой не создан
```

### 7.2 Карта мира и дорожная карта

```gherkin
Сценарий: Просмотр карты мира                       [api][ui]
  Дано есть герой уровня 1
  Когда GET /api/map
  Тогда видны регионы со статусами open/locked
  И локации стартового региона имеют статус available/locked согласно пререквизитам
  И UI рисует карту в RPG-стиле с индикатором прогресса
```

### 7.3 Прохождение квеста (с практикой)

```gherkin
Сценарий: Завершение практического квеста начисляет XP   [api]
  Дано герой в доступной теме, квест practice (xp = 150) не завершён
  Когда POST /api/quests/{id}/complete с валидной сдачей
  Тогда total_xp += 150, статус квеста = completed
  И прогресс темы обновлён в ответе

Сценарий (идемпотентность, граничный): Повторная сдача    [api]
  Дано квест уже completed
  Когда POST /api/quests/{id}/complete ещё раз
  Тогда XP НЕ начисляется повторно, статус остаётся completed

Сценарий (негативный): Невалидная сдача                   [api]
  Дано доступный квест
  Когда POST .../complete с невалидным submission
  Тогда ответ 422, XP не начислен, статус не изменён
```

### 7.4 Повышение уровня и разблокировка

```gherkin
Сценарий: Level-up открывает новый регион            [unit][api]
  Дано герой с total_xp на 1 ниже порога уровня 2, и регион R требует уровня 2
  Когда завершён квест, добавивший достаточно XP
  Тогда level_for_xp вырос на 1
  И recompute_unlocks открывает регион R
  И ответ /complete содержит флаг level_up и список новых разблокировок
  И UI показывает LevelUpOverlay (RPG-событие)

Сценарий (граничный): XP ровно на пороге уровня      [unit]
  Дано total_xp == порогу уровня N
  Тогда level_for_xp == N (не N-1 и не N+1)
```

### 7.5 Доступ к заблокированной локации (негативный)

```gherkin
Сценарий: Вход в локацию ниже требований             [api]
  Дано локация требует уровня выше текущего ИЛИ незавершённый пререквизит
  Когда GET /api/topics/{id} или POST /api/quests/{id}/complete
  Тогда ответ 423 Locked с описанием условий разблокировки (RPG-текст)
  И никакой XP не начислен
```

### 7.6 Сохранение и восстановление прогресса (граничный)

```gherkin
Сценарий: Прогресс переживает перезапуск             [api][e2e]
  Дано герой прошёл часть квестов (известный total_xp и статусы)
  Когда бэкенд перезапущен (StateStore = Postgres)
  Тогда GET /api/hero и /api/map возвращают тот же уровень, XP и статусы без потерь
```

### 7.7 Динамическая генерация события (GLM + фоллбэк)

```gherkin
Сценарий: Генерация события в каноне RPG              [api]
  Дано герой в локации, поддерживающей события, StoryGenerator = SeedBankAdapter
  Когда POST /api/locations/{id}/event
  Тогда возвращается русский текст события (source: "bank"), встроенный в контекст
  И событие сохранено в story_event

Сценарий: Живая генерация через GLM                   [api]
  Дано задан GLM_API_KEY, StoryGenerator = GlmAdapter (замокан на детерм. ответ)
  Когда POST /api/locations/{id}/event
  Тогда возвращается русский текст события с source: "glm"

Сценарий (фоллбэк, негативный): GLM недоступен        [api]
  Дано GlmAdapter бросает ошибку провайдера (нет ключа/таймаут/5xx)
  Когда POST /api/locations/{id}/event
  Тогда ответ 200 с событием из банка (source: "bank"), факт фоллбэка залогирован
  И прохождение квестов остаётся доступным
```

  Когда клиент шлёт total_xp/level в любом запросе (hero/complete)

## 8. Количественные критерии выполнения

Все — измеримые, проверяемые автоматически, без возможности «мухлевать» (отключение
теста/заглушка нарушает критерий).

**Тесты и покрытие:**

- Покрытие веток (branch) бэкенда ≥ **85 %**; модуль `progression` — **100 %** строк и веток.
- Mutation score (mutmut) на `progression` + `quests` ≥ **70 %**.
- Каждый BDD-сценарий §7 имеет ≥1 автотест; 100 % тестов зелёные; `skip`/`xfail` —
  только с обоснованием в комментарии. Маркер `live_llm` исключён из обязательного прогона.
- В истории работы видны **упавшие тесты (RED) до реализации** (требование TDD).

**Статический анализ:**

- Python: `mypy --strict` — 0 ошибок; `ruff check` — 0 ошибок; `ruff format` — без диффов.
- TS: `tsc --noEmit` (strict) — 0 ошибок; `eslint` — 0 ошибок; `prettier --check` — без диффов.
- Нет `any` / `# type: ignore` / `@ts-ignore` без обоснования в комментарии.

**Производительность (нагрузочно, не-LLM эндпоинты):**

- `GET /api/map`, `/api/hero`, `POST /complete`: **p95 < 200 мс** при 50 rps на типовом
  seed (~5 регионов, ~30 тем). Замер автоматизирован (нагрузочный тест в CI или скрипт).
- `/event` через банк (`SeedBankAdapter`): **p95 < 200 мс**. Через GLM (`GlmAdapter`)
  исключён из порога (внешняя латентность); таймаут на провайдера **≤ 8 с**, после —
  фоллбэк на банк (всё равно `200`).

**Запуск и контент:**

- `docker compose up` поднимает frontend+backend+db **без ключа** (фоллбэк-банк);
  healthcheck'и зелёные. Живая генерация включается опционально через `GLM_API_KEY`
  (+`GLM_BASE_URL`) в `.env`. Есть `.env.example`.
- Схема контента: тест доказывает, что **каждая тема** имеет ≥1 `kind=practice`, а граф
  пререквизитов — DAG.
- Анти-чит: тест доказывает, что клиент не может выставить XP/уровень в обход правил.

**UI-язык:**

- Все пользовательские строки — из словаря `ru.ts`; тест/линт-правило флагует
  hard-coded не-русские строки в сценах (кроме спец-терминов из whitelist).

**Визуал (RPG-атмосфера, §10):**

- 0 растровых ассетов в UI-хроме (всё SVG/CSS) — проверяется тестом/линтом.
- 100% пользовательских цветов через design tokens (нет hard-coded hex вне темы) — линт.
- Снапшот-тесты ключевых компонентов (`XpBar`, `QuestIcon`, `LocationMarker`,
  `LevelUpOverlay`, SVG-карта) зелёные; арты-плейсхолдеры не ломают сцены без ключа.

## 9. Алгоритмы и сложность

Обозначения: `L` — число уровней (~50), `V` — число тем, `E` — рёбер пререквизитов,
`P` — пререквизитов у темы, `Q` — квестов в теме.

| Операция | Подход / структура | Время | Память |
|----------|--------------------|-------|--------|
| `level_for_xp(xp)` | предвычисленный неубывающий массив кумулятивных порогов + **бинарный поиск** | `O(log L)` | `O(L)` |
| `xp_to_next_level` | тот же массив, разность | `O(log L)` | `O(L)` |
| `award_xp` | прибавление + один `level_for_xp` | `O(log L)` | `O(1)` |
| Валидация DAG пререквизитов | топологическая сортировка (Kahn) при `catalog.load()` | `O(V + E)` | `O(V + E)` |
| `recompute_unlocks` | обход тем: проверка `unlock_level` + завершённости пререквизитов | `O(V + E)` | `O(V)` |
| Проверка доступности 1 локации | пересечение со множеством завершённых тем | `O(P)` | `O(1)` |
| Поиск региона/темы/квеста по id | hash-map индекс, построен при загрузке | `O(1)` | `O(V + Σ Q)` |
| `complete_quest` | доступность `O(P)` + `award_xp` `O(log L)` + persist `O(1)` | `O(P + log L)` | `O(1)` |

**Обоснование структур:**

- **Массив порогов + бинарный поиск** вместо замкнутой формулы: пороги задаются дизайном
  (могут быть нелинейными), массив даёт гибкость и `O(log L)`; `L` мал, но бинарный поиск
  делает функцию устойчивой к росту таблицы.
- **Adjacency-list + Kahn** для пререквизитов: естественно для DAG, ловит циклы при загрузке
  (fail fast), `recompute_unlocks` линеен.
- **Hash-индекс** контента строится один раз при `load()`; запросы карты/темы — `O(1)` на
  лукап, что держит p95 эндпоинтов в бюджете.

## 10. Графика и визуальная идентичность

Подход — **гибрид** (решено на шаге 4):

- **UI-хром и карта — SVG/CSS, делаются в коде** (этап E7v плана): рамки, кнопки, полоса
  XP, оверлей level-up, иконки квестов (theory=свиток, practice=наковальня, boss=череп),
  маркеры локаций, значки лута, стилизованная SVG-карта. Векторно, в git, тестируемо.
  Design tokens: палитра «тёмное фэнтези», типографика, тени/виньетки.
- **Рисованные арты — через шов `AssetGenerator`** (этап E9): портреты классов героя,
  фоны локаций, боссы. Adapters: `FluxAdapter` (Flux через Replicate/fal, ключ
  `REPLICATE_API_TOKEN`) и `PlaceholderAdapter` (детерминированные SVG-плейсхолдеры —
  работа без ключа и тесты). Генерация **офлайн/build-time** (скрипт → файлы в
  `frontend/src/theme/assets/` → коммит), горячий путь не ходит в сеть.

**Измеримый критерий визуала** (§8): 0 растровых ассетов в UI-хроме (всё SVG/CSS); 100%
цветов через design tokens; снапшот-тесты ключевых компонентов зелёные; арты-плейсхолдеры
не ломают сцены при отсутствии ключа.

**Почему так:** UI-хром в SVG/CSS даёт консистентный олдскульный вид, чёткость на любом
DPI и версионирование; рисованные арты, которые код не сделает, — за швом, так что выбор
провайдера (Flux/иной) — это adapter, а не переделка. «Использовать сам Claude Code как
генератор картинок» невозможно — нужен внешний диффузионный провайдер за швом.

## 11. Документация решений (почему так)

- **Python/FastAPI на бэкенде (а не Node).** Выбран пользователем; плюс — глубоко
  проработанный `python-guidelines.md`, `mypy --strict`, `mutmut`. Отвергнута альтернатива
  «TS end-to-end»: единый язык удобнее, но Python-гайд в репозитории строже и даёт более
  надёжную бизнес-логику для критериев анти-чита/покрытия.
- **Один локальный игрок, без auth (MVP).** Минимум кода, фокус на геймплее/прогрессе.
  Отвергнут «мультиюзер»: auth/сессии/изоляция — большой объём, не нужен для цели «учиться
  каждый день». Оставлен **шов** `StateStore` с ключом героя, чтобы добавить пользователей
  позже без переписывания ядра.
- **Гибридный контент (seed + LLM).** Каркас детерминирован → тестируем и стабилен; живость
  даёт LLM на событиях. Отвергнут «весь контент через LLM»: недетерминизм ломает критерии
  покрытия и воспроизводимость прогресса.
- **События — комбо GLM + фоллбэк-банк за швом `StoryGenerator`.** «Использовать сам
  Claude Code в рантайме» невозможно (работающее приложение не вызывает терминального
  агента), поэтому провайдер — внешний API за швом. Выбран GLM Coding Plan: его
  Anthropic-совместимый эндпоинт делает `GlmAdapter` тем же кодом, что и любой
  Claude-адаптер (отличие — `base_url`+ключ), а смена провайдера в будущем — это новый
  adapter, не переделка. `SeedBankAdapter` даёт работу без ключа, детерминизм тестов и
  фоллбэк при сбое — это снимает противоречие §2.1. Отвергнут прямой вызов SDK из
  эндпоинта (нетестируемо, ломает направление зависимостей) и «жёстко обязательный LLM»
  (ломает «запуск без ручных шагов»).
- **Контент в файлах, не в БД.** Источник истины — версионируемый seed (review через git),
  валидируется при загрузке. Отвергнут «контент в БД»: усложняет ревью и миграции ради
  гибкости, не нужной в MVP.
- **XP/уровни считаются только на сервере.** Анти-чит — серверный инвариант, клиент не
  может задать XP/level. Отвергнут расчёт на клиенте: критерий «нельзя намухлевать»
  требует серверной проверки.
- **SQLAlchemy синхронный, а не async (E5).** Всё ядро/quests/api синхронные; async-БД
  потребовал бы переписать их целиком ради одного локального игрока. Синхронные эндпоинты
  FastAPI исполняются в threadpool — для single-player достаточно. Отвергнут async как
  преждевременная сложность; шов `StateStore` позволит перейти на async позже без правки ядра.
- **Схема через `create_all` при старте, Alembic отложен (E5).** Для MVP с фиксированной
  схемой `create_all` идемпотентно создаёт таблицы при старте без ручных шагов. Alembic
  (версионирование миграций) добавится, когда схема начнёт эволюционировать — это не меняет
  интерфейс `StateStore`.
- **Безопасность от гонки `complete` (E5).** Двойное начисление XP предотвращается на уровне
  БД: `UNIQUE(hero_id, quest_id)` + относительный SQL-инкремент `total_xp` в одной транзакции.
  Проигравший гонку получает IntegrityError → откат → 0 начислений. Подтверждено тестом с
  двумя потоками.

## 12. Открытые вопросы (РЕШЕНО на шаге плана)

1. **Кривая XP** — квадратичная: порог уровня `N` = `base_xp * N²`, `base_xp` в seed.
2. **Сдача практического квеста** — **квиз с автопроверкой**; эталонные ответы только
   на сервере (анти-чит), клиенту не отдаются.
3. **Классы героя** — **модификаторы XP** по регионам (`class_modifier`, см. §4.3).
4. **Объём MVP** — 3–4 региона (ML → LLM → RAG → Агенты), ~12 тем.

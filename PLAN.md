## 1. Как это работает (логика системы)

Прежде чем планировать — проговорённая модель работы (от чего отталкиваются этапы):

**Единица истины — суммарный XP героя.** Уровень не хранится как состояние, а
вычисляется из `total_xp` функцией `level_for_xp` (квадратичная кривая `base_xp*N²`).
Это исключает рассинхрон «уровень ⨯ XP» и делает анти-чит простым: клиент не может
прислать уровень — он производный.

**Прохождение квеста — единственный путь изменения XP.** Поток `complete_quest`:
1. Найти квест в `catalog` (иначе `QuestNotFound`).
2. Проверить доступность темы через `recompute_unlocks` (уровень ≥ `unlock_level`
   региона И все пререквизиты темы завершены), иначе `LocationLocked` → HTTP `423`.
3. Если квест уже `completed` — вернуть текущее состояние **без повторного начисления**
   (идемпотентность).
4. Проверить сдачу: для `practice` — сверить ответы квиза с эталоном (хранится только на
   сервере); невалидно → `InvalidSubmission` → `422`.
5. Вычислить множитель класса `class_modifier(hero.class, quest.region)` и начислить
   `award_xp(state, quest.xp, modifier)` → новый `total_xp` + факт level-up.
6. Сохранить статус квеста и `total_xp` через `StateStore`.
7. Пересчитать анлоки; вернуть `CompletionResult` (новый уровень, level_up?, новые
   разблокировки, лут).

**Карта мира — проекция.** `GET /api/map` = `catalog` + `recompute_unlocks(hero)`:
регионы `open/locked` по уровню, локации `available/locked/completed` по пререквизитам и
статусам квестов. Чистая функция от (контент, состояние) — легко тестируется и кэшируется.

**События — украшение, не блокирующее прогресс.** `/event` идёт через шов
`StoryGenerator`: если задан `GLM_API_KEY` — `GlmAdapter` генерирует текст на лету; при
сбое/таймауте/без ключа — `SeedBankAdapter` отдаёт детерминированное событие из банка.
Ответ всегда `200` с пометкой `source: glm|bank`. Падение LLM никогда не ломает квесты.

**Направление зависимостей.** Ядро (`progression`, `catalog`, `quests`) не знает про
HTTP/БД/LLM. Всё внешнее — адаптеры на швах (`StateStore`, `ContentSource`,
`StoryGenerator`, `api`). Это и есть тестовая поверхность: ядро тестируется через
интерфейсы с in-memory адаптерами, без сети и БД.

**Почему такой порядок этапов.** Сначала каркас (E0) проверяет, что всё поднимается и
статика зелёная. Затем — самый глубокий и чистый модуль `progression` (E1): он не зависит
ни от чего, даёт максимум уверенности на единицу усилий. `catalog` (E2) и `quests` (E3)
наращивают доменное ядро. `api` (E4) и Postgres (E5) выводят ядро наружу. `StoryGenerator`
(E6) добавляет события. Фронтенд (E7a/E7b) опирается на готовый стабильный API. E8
закрывает нефункциональные критерии и весь DoD.

## E1 — Ядро `progression` (самый глубокий модуль)

**Цель.** Чистые функции прогресса. Без I/O. Это deep-модуль с маленьким интерфейсом.

**Интерфейс (SPEC §4.3):** `level_for_xp`, `xp_to_next_level`, `class_modifier`,
`award_xp(state, base_amount, modifier)`, `recompute_unlocks(hero, catalog)`.

**TDD-срезы (по одному тесту → реализация):**
1. `level_for_xp`: уровень 1 при xp=0; **граничный** — xp ровно на пороге `base_xp*N²`
   даёт `N`, на 1 меньше — `N-1` (SPEC §7.4 граничный).
2. `xp_to_next_level`: остаток до следующего порога; на максимуме — 0.
3. `class_modifier`: ×1.1 для класса в его регионе, ×1.0 иначе; неизвестный регион → ×1.0.
4. `award_xp`: начисляет `round(base*modifier)`, не мутирует вход (новый объект);
   `ValueError` при `base<=0`/`modifier<=0`; флаг `level_up` при пересечении порога (§7.4).
5. `recompute_unlocks`: регион open при `level≥unlock_level`; тема available при open-регионе
   и всех завершённых пререквизитах; иначе locked (§7.5 логика).

**Алгоритмы (SPEC §9):** массив кумулятивных порогов + бинарный поиск `O(log L)`;
обход анлоков `O(V+E)`. Зафиксировать в докстрингах.

**Закрывает:** §7.4 (unit-часть), §9, §8 (`progression` — 100% строк/веток).
**Критерий завершения:** 100% покрытие `progression`; mutation score ≥70%; `mypy --strict`,
`ruff` чисто; видимые RED→GREEN в истории. **Оценка:** 1 день.

## E2 — `catalog` + seed-схема + валидация + MVP-контент

**Цель.** Загрузка и строгая валидация контента; авторский seed на 3–4 региона / ~12 тем.

**Интерфейс (SPEC §4.3):** `load() -> Catalog`; `region/topic/quest(id)`;
`prerequisites(topic_id)`; индексы-хэшмапы `O(1)` на лукап. Шов `ContentSource`
(`YamlContentSource` + `InMemorySource`).

**TDD-срезы:**
1. Загрузка валидного минимального seed → доступны регионы/темы/квесты по id.
2. **Негатив:** тема без `kind=practice` → ошибка валидации (§7.9).
3. **Негатив:** цикл в пререквизитах → ошибка (Kahn, граф обязан быть DAG) (§7.9).
4. Дубликат id / висячая ссылка пререквизита → ошибка (fail fast).
5. Невозрастающие `unlock_level` регионов — проверка инварианта.
6. Парсинг `progression.base_xp`, `progression.max_level` и `classes[].modifiers` из seed.
7. Флаг `events: true|false` у локации (поддерживает ли тема сюжетные события) — парсинг
   и дефолт; нужен для `/event` (E6).

**Контент MVP (после зелёных тестов схемы):** регионы ML → LLM → RAG → Агенты, ~12 тем,
у каждой ≥1 практический квест с квизом (эталоны `answer` только на сервере), 3–5 классов
с модификаторами. Пороги `base_xp` подобрать так, чтобы новый регион открывался за
разумное число квестов.

**Закрывает:** §7.9, §8 «контент» (каждая тема ≥1 practice; DAG).
**Критерий завершения:** все инварианты покрыты тестами; seed проходит валидацию; покрытие
ветвей ≥85%. **Оценка:** 1–1.5 дня.

## E3 — `quests` (оркестрация прохождения)

**Цель.** Единственный модуль, меняющий XP/статусы. Связывает `catalog`+`progression`+`StateStore`.

**Интерфейс (SPEC §4.3):** `complete_quest(quest_id, submission) -> CompletionResult`.
Шов `StateStore` — здесь используется `InMemoryStore` (Postgres — E5).

**TDD-срезы (поток из §1):**
1. Валидная сдача квиза практического квеста → XP += `round(xp*modifier)`, статус
   `completed`, прогресс темы обновлён (§7.3).
2. **Граничный/идемпотентность:** повторная сдача завершённого → XP не меняется (§7.3).
3. **Негатив:** неверные ответы квиза → `InvalidSubmission`, XP/статус не меняются (§7.3).
4. **Негатив:** квест в заблокированной теме → `LocationLocked` (§7.5).
5. Level-up по завершении: новый уровень + список новых разблокировок (§7.4 api-часть).
6. `QuestNotFound` для несуществующего id.

**Закрывает:** §7.3, §7.5 (доменная логика), §7.4 (оркестрация level-up).
**Критерий завершения:** mutation score ≥70% на `quests`+`progression`; покрытие ≥85%;
статика чисто. **Оценка:** 1 день.

## E4 — HTTP API (FastAPI adapter) + анти-чит

**Цель.** Тонкий HTTP-слой поверх ядра. Pydantic-DTO, маппинг доменных ошибок → коды.

**Эндпоинты (SPEC §6):** `POST/GET /api/hero`, `GET /api/map`, `GET /api/topics/{id}`,
`POST /api/quests/{id}/complete`. Тесты через httpx + ASGI с `InMemoryStore`.

**Инфраструктура (из аудита):**
- **CORS** настроен для origin фронтенда (docker compose: разные порты) — иначе UI не
  достучится. Origin берётся из env.
- **`catalog.load()` — один раз при старте** (app lifespan), индекс кэшируется; на запрос
  идёт `O(1)`-лукап (держит p95, SPEC §9). Тест: повторные запросы не перечитывают seed.

**TDD-срезы:**
1. `POST /api/hero` (имя/класс/аватар) → герой уровня 1, `total_xp=0`; `GET /api/map`
   показывает один открытый стартовый регion (§7.1).
2. **Негатив:** повторный `POST /api/hero` → `409` (§7.1).
3. **Граничный:** пустое / >40 символов имя → `422` (§7.1).
4. `GET /api/map` → статусы регионов/локаций (§7.2 api-часть).
5. **Позитив:** `GET /api/topics/{id}` доступной темы → `200` с квестами (без эталонов квиза).
6. `GET /api/topics/{id}` заблокированной темы → `423` с RPG-условиями (§7.5 api).
7. `POST /complete` happy/идемпотентность/невалидная сдача → коды 200/200/422.
8. **Анти-чит:** клиент шлёт `total_xp`/`level` в `hero`/`complete` → поля игнорируются,
   XP меняется только через квесты (§7.8). Эталоны квиза не присутствуют в ответах API.

**Закрывает:** §7.1, §7.2(api), §7.5(api), §7.8.
**Критерий завершения:** все api-сценарии зелёные; OpenAPI-схема генерится; статика чисто;
покрытие ≥85%. **Оценка:** 1–1.5 дня.

## E5 — Персистентность (Postgres + `SqlAlchemyStore`)

**Цель.** Боевой адаптер `StateStore` на PostgreSQL; прогресс переживает перезапуск.

**Состав:** SQLAlchemy 2.0 (async) модели `hero`/`quest_progress`/`story_event` (SPEC §5.2);
миграции (Alembic); `SqlAlchemyStore` реализует тот же интерфейс, что `InMemoryStore`
(доказывает реальность шва — два адаптера).

**TDD-срезы (интеграционные, тестовый Postgres):**
1. `save_hero`/`load_hero` round-trip сохраняет `total_xp` и статусы.
2. **Граничный (§7.6):** пройти часть квестов → «перезапуск» (новая сессия/процесс) →
   `GET /api/hero` и `/api/map` дают те же уровень/XP/статусы.
3. Уникальность `(hero_id, quest_id)`; повторный complete не плодит строки.
4. **Конкурентность (из аудита):** два одновременных `POST /complete` одного квеста →
   XP начислен **ровно один раз** (транзакция + `UNIQUE(hero_id, quest_id)`; конфликт
   обрабатывается как идемпотентный повтор). Защищает от двойного начисления в гонке.
5. Готовность: `/health/ready` отражает доступность БД (liveness `/health` — из E0).

**Закрывает:** §7.6 + серверный инвариант от гонки.
**Критерий завершения:** интеграционные тесты зелёные на Postgres; `docker compose up`
с БД работает; миграции применяются автоматически при старте. **Оценка:** 1 день.

## E6 — `StoryGenerator` (GLM + фоллбэк) + `/event`

**Цель.** События за швом: GLM основной, банк — фоллбэк/тесты; `/event` всегда `200`.

**Состав (SPEC §4.3, §7.7):** интерфейс `generate_event(ctx) -> StoryEvent`;
`SeedBankAdapter` (детерминированный банк событий в seed), `GlmAdapter` (Anthropic-совместимый
SDK: `base_url`+ключ из env), обёртка с таймаутом ≤8с и **молчаливым фоллбэком** на банк;
**валидация выхода** (из аудита): русский язык, лимит длины, без управляющих/служебных
последовательностей — невалидный ответ трактуется как сбой → фоллбэк; сохранение в
`story_event`. `/event` доступен только для локаций с `events: true` (E2).

**TDD-срезы:**
1. Банк: `/event` без ключа → русский текст, `source:"bank"`, событие сохранено (§7.7).
2. GLM (замокан детерминированно): с ключом → `source:"glm"` (§7.7).
3. **Фоллбэк/негатив:** `GlmAdapter` бросает (таймаут/5xx/нет ключа) → `200` из банка,
   факт фоллбэка залогирован; квесты доступны (§7.7).
4. **Мусорный ответ GLM (из аудита):** не-русский / превышение длины / пустой →
   валидация отклоняет → фоллбэк на банк (`source:"bank"`).
5. Живой тест `@pytest.mark.live_llm` (вне обязательного прогона/покрытия).

**Закрывает:** §7.7.
**Критерий завершения:** все не-live тесты зелёные и детерминированы (без сети); фоллбэк
доказан тестом; статика чисто. **Оценка:** 1 день.

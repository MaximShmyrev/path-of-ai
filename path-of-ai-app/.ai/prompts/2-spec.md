# Шаг 2. Составить спецификацию

> Вставь описание задачи из шага 1 вместо `<Вставить описание задачи>` и отправь
> LLM. Результат — файл `SPEC.md` в корне проекта.

---

Используя моё описание, создай **спецификацию разработки** и сохрани её в
`SPEC.md`.

<Вставить описание задачи (см. 1-task.md)>

Спецификация **должна включать**:

1. **Контекст проекта и индекс спецификации — в первых 200 строках файла.**
   Чтобы любой раздел можно было быстро найти, а LLM — загрузить контекст с
   начала файла.

2. **Описание архитектуры.** Используй **skill `improve-codebase-architecture`**.
   Опиши модули, их интерфейсы (что обязан знать вызывающий), швы (seams) для
   тестируемости, направление зависимостей. Применяй термины глоссария скилла
   (module / interface / implementation / depth / seam / adapter).

3. **Подробные сценарии тестов** на основе описанных мной пользовательских
   сценариев — в формате BDD (Given / When / Then), включая негативные и
   граничные случаи. Каждый мой сценарий → минимум один тест-сценарий.

4. **Количественные критерии выполнения задачи.** Измеримые, проверяемые
   автоматически, без возможности «мухлевать» (см. раздел «Критерии» в
   `@Styleguide`). Укажи целевые значения покрытия, mutation score, latency и т.п.

5. **Алгоритмы и сложность.** Для ключевых операций укажи ожидаемую сложность
   (Big-O по времени и памяти) и обоснуй выбор структур данных.

6. **Changelog** с описанием изменений (в конце файла; пополняется по мере
   развития спеки).

7. **Документацию с аргументированным выбором подхода.** Для каждого значимого
   решения — почему именно так, какие альтернативы рассмотрены и отвергнуты.

Следуй правилам `@Styleguide` (`.ai/rules/styleguide.md`) и язык-специфичному
гайду.

Если в задаче есть пробелы или противоречия — задай уточняющие вопросы **до**
написания спеки.

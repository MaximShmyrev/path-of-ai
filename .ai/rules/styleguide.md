# Styleguide (ядро, language-agnostic)

Это **корневой гайд по стилю и качеству** для всех проектов на базе `sdd-kit`.
Промпты воркфлоу (`.ai/prompts/`) ссылаются на него как на `@Styleguide`.

Гайд состоит из двух частей:

1. **Контроль качества** — что обязательно соблюдать в любом проекте (слайд «Как
   контролировать качество»).
2. **Definition of Done** — измеримый чеклист, по которому задача считается
   выполненной.

Язык-специфичные правила — в отдельных файлах:

- [python-guidelines.md](python-guidelines.md) — Python (заполненный пример).
- [typescript-guidelines.md](typescript-guidelines.md) — TypeScript (скелет).

> При старте нового проекта: оставьте этот файл как ядро, выберите/заполните
> язык-специфичный гайд, удалите ненужные.

---

## 1. Контроль качества

Девять принципов. Каждый — обязателен, если в `1-task.md` не указано обратное явно.

### 1.1 BDD — сценарии в структурном виде

Поведение описывается до кода в формате **Given / When / Then**. Сценарии живут
в спецификации (`2-spec.md`) и становятся основой тестов.

```gherkin
Сценарий: Пользователь оплачивает корзину с валидными данными
  Дано корзина содержит 2 товара на сумму 1000
  Когда пользователь подтверждает оплату валидной картой
  Тогда заказ переходит в статус "paid"
  И пользователь получает чек
```

Каждый пользовательский сценарий из задачи → минимум один BDD-сценарий → минимум
один тест.

### 1.2 TDD — сначала тест, потом код

Используйте **skill `tdd`**. Цикл red → green → refactor, **вертикальными
срезами** (один тест → одна реализация → повтор), а не «все тесты, потом весь
код».

- В начале работы должны быть **видимые упавшие тесты** (RED). Это обязательное
  требование заказчика.
- Только после красного теста пишется код, делающий его зелёным (GREEN).
- Затем — рефакторинг без изменения поведения (REFACTOR).

Тесты проверяют поведение через публичный интерфейс, а не детали реализации.

### 1.3 Критерии — измеримые и без возможности «мухлевать»

Критерии выполнения задачи должны быть **количественными** и проверяемыми
автоматически. Формулировка «работает хорошо» запрещена.

| ❌ Плохо | ✅ Хорошо |
|---------|----------|
| «Покрытие высокое» | «Покрытие веток ≥ 85 %, проверяется в CI» |
| «Быстро отвечает» | «p95 latency < 200 мс при 100 rps» |
| «Тесты проходят» | «100 % тестов зелёные; 0 пропущенных без причины» |
| «Код чистый» | «Линтер 0 ошибок; mypy/tsc 0 ошибок» |

Критерий не должен поддаваться обходу (например, отключением теста или
заглушкой). Если критерий можно «обмануть» — он сформулирован неверно.

### 1.4 Styleguide — единый стиль кода

Соблюдайте этот файл + язык-специфичный гайд. Новый код должен быть неотличим по
стилю от окружающего: именование, плотность комментариев, идиомы.

### 1.5 Строгая типизация и AST-анализ

Компилятор / строгий линтер валидируют часть кода **до** запуска.

- Включайте максимально строгий режим типов (`mypy --strict`, `tsc --strict`).
- Линтер с авто-фиксом обязателен (`ruff`, `eslint`).
- 0 ошибок типов и 0 ошибок линтера — часть Definition of Done.
- Избегайте `any` / `# type: ignore` без обоснования в комментарии.

### 1.6 Мутационное тестирование

Тесты в нестандартных и негативных ситуациях вскрывают неочевидные проблемы.
Прогоняйте мутационное тестирование на ключевой бизнес-логике (`mutmut` для
Python, `stryker` для TS).

- Цель: mutation score ≥ 70 % на модулях с бизнес-логикой.
- Выжившие мутанты — сигнал слабых или отсутствующих тестов, а не повод снизить
  порог.

### 1.7 Чеклисты — строгое выполнение пунктов

Definition of Done (раздел 2) — это чеклист. Проходить по нему пункт за пунктом,
ничего не пропуская. «Кажется, готово» — не критерий.

### 1.8 Чистая архитектура

Используйте **skill `improve-codebase-architecture`**. Принципы:

- Понятная, легко читаемая структура кода и проекта.
- **Глубокие модули**: много поведения за маленьким интерфейсом.
- Зависимости направлены внутрь (бизнес-логика не знает про фреймворк/БД/HTTP).
- Швы (seams) для подмены поведения без правки на месте.
- Тест поведения через интерфейс, а не через детали.

### 1.9 Алгоритмы и сложность

Учитывайте алгоритмы и структуры данных **явно**. В спецификации и плане
указывайте ожидаемую сложность ключевых операций (Big-O по времени и памяти) и
обосновывайте выбор структуры данных. Проговаривайте это в диалоге с LLM.

## 2. Definition of Done

Задача считается выполненной, только когда **все** пункты выполнены и
подтверждены командами. Подтверждайте фактами (вывод команд), а не словами.

### Тесты
- [ ] Есть BDD-сценарии на каждый пользовательский сценарий из задачи.
- [ ] В истории работы видны упавшие тесты (RED) до реализации.
- [ ] 100 % тестов зелёные; пропуски (`skip`/`xfail`) обоснованы комментарием.
- [ ] Покрытие веток ≥ целевого (по умолчанию 85 %).
- [ ] Mutation score ≥ 70 % на модулях с бизнес-логикой (если применимо).

### Статический анализ
- [ ] Линтер: 0 ошибок.
- [ ] Типы: 0 ошибок в строгом режиме (`mypy --strict` / `tsc --strict`).
- [ ] Форматтер прогнан; диффов нет.
- [ ] Нет `any` / `type: ignore` / подавлений без обоснования.

### Критерии задачи
- [ ] Все количественные критерии из спецификации выполнены и измерены.
- [ ] Каждый критерий проверен автоматически (не на словах).

### Архитектура и код
- [ ] Структура соответствует спецификации; швы на месте.
- [ ] Указана и соблюдена сложность ключевых операций (Big-O).
- [ ] Код соответствует этому styleguide и язык-специфичному гайду.

### Документация
- [ ] Обновлён changelog (в спеке и в плане).
- [ ] Решения с аргументацией зафиксированы (почему такой подход).

> Если хоть один пункт не выполнен — задача **не готова**. Сообщите, какой именно
> пункт не пройден и почему, не выдавая незавершённое за готовое.

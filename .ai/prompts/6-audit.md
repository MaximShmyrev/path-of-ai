# Шаг 6. Делать аудит

> Финальная проверка после реализации всех этапов. Независимый взгляд: ищем
> дыры, а не подтверждаем «и так норм».

---

Проведи **аудит** готовой работы против задачи, `SPEC.md` и `PLAN.md`.

### 1. Соответствие спецификации
Используй **skill `review`** (две оси: Standards + Spec). Проверь, что код
реально реализует спеку, а не её упрощённую версию. Составь таблицу
«критерий из SPEC → подтверждение (команда/тест) → статус».

### 2. Definition of Done
Пройди **весь чеклист DoD** из `@Styleguide` пункт за пунктом. Для каждого —
факт (вывод команды), а не слова. Любой непройденный пункт = задача не готова.

### 3. Тесты на прочность
- **Мутационное тестирование** на модулях с бизнес-логикой (`mutmut`/`stryker`).
  Выжившие мутанты → недостающие тесты. Цель — mutation score ≥ 70 %.
- Негативные и граничные случаи: пустые входы, лимиты, отказы внешних систем,
  конкурентность.

### 4. Статический анализ и безопасность
- Линтер + строгая типизация: 0 ошибок, нет необоснованных подавлений.
- Используй **skill `security-best-practices`** для проверки уязвимостей
  (если применимо к языку/фреймворку).

### 5. Архитектура и сложность
Используй **skill `improve-codebase-architecture`**: не появились ли мелкие
(shallow) модули, протечки абстракций, нарушения направления зависимостей.
Проверь, что фактическая сложность ключевых операций совпадает с заявленной.

### Итог
- Список найденных проблем по приоритету (critical / major / minor).
- Что чинить и как.
- Честный вердикт: **готово / не готово** с обоснованием. Не выдавай
  незавершённое за готовое.
